Because `DocumentStore.__init__` and `SqliteIngestState.__init__` call `migrate()` (RI-5), the first process of any kind that opens the 3.5 GB main DB after a new `migrations/0007_*.sql` lands (an MCP server start, the dashboard) applies it with no backup; July's five `papers.db.bak-pre-*` copies were hand-made precisely because that automation did not exist. `rag/document_store.py:120` sets `journal_mode=WAL`, `foreign_keys=ON`; no `busy_timeout` anywhere in `rag/` or `app/` (grep: none; Python's default 5 s applies). WAL files exist in all five corpora (and all five `mcp_usage.db`), 0 bytes WAL: they are persisted residue of WAL mode, not evidence of an open writer. `lsof` on main `papers.db*` right now shows only read-only review scripts (pids 3649045, a sibling review lane, and my own query). Concurrent-writer protection is by convention: `.ingest.lock` and `.pass1.lock` files and the dashboard's `.control.lock`, all per-corpus.
  `app/snapshot.py::backup_sqlite` is correct (read-only source + `VACUUM INTO`), but `app/corpus_integrity.py` opens the live DB read-write (see F-A4) and `snapshot` never runs `PRAGMA integrity_check`.
- Impact: low probability, high cost: a bad `0007` migration on the source of truth with no fresh backup (and F-A1's backup is 3.5 months old) is the one operation that can corrupt data in place. A 5 s busy timeout under a long ingest transaction plus a dashboard query yields `database is locked` errors in readers [INFERRED].
- Checklist dimension: reversibility / reliability.
- Proposed change: before applying any pending migration to an existing non-empty DB, `migrate()` is foundation-protected, so do it at the callers: add to `app/assembly.py` a guard `if pending_migrations(db) and db_size>0: refuse unless an `app.snapshot` newer than N hours exists, else print "run python -m app.snapshot first"`; or simplest, a RUNBOOK rule plus `doctor` check "pending migrations: N; newest backup age: X". Set `PRAGMA busy_timeout=30000` in `DocumentStore.__init__` and `usage_log` readers. Add `PRAGMA quick_check` to `snapshot`.
- Needs: GPU no; foundation-protected partly (any `migrate()` edit is protected; the doctor/assembly route avoids it); operator sign-off yes only for a `migrate()` change; re-embed no.
- How to verify: doctor test with a fake pending migration and no recent backup reports an issue; pass = non-zero exit.

### F-A8 The GPU lock is a mutex without holder identity or priority; lock-timeout errors are scored as misses  (severity: medium)
- Evidence [VERIFIED]: `rag/gpu_lock.py:25-42` (`FileLock`, no metadata); `docs/AGENT-OPERATIONS-LESSONS.md:722-760` §9.1 and `docs/eval-reports/2026-08-28-sb1-chunk-boundary.md` §0: three concurrent GPU jobs, two eval jobs sat >20 min in `gpu_lock.acquire` and "a handful of their questions eventually hit `gpu_lock_timeout=300s` and errored out — silently scored as ordinary misses by `app/retrieval_eval.py`'s per-hit resilience". The TransientError message at timeout is "likely held by a stale or wedged process; check for a stuck holder" (`rag/gpu_lock.py:38-41`): it does not name the holder; an operator needs `fuser .gpu.lock` + a `/proc` scan (what SB-1 did by hand). The lock does not govern Ollama or any non-adapter GPU user (F-A3). The lessons file records the rule "order GPU jobs cheapest-first" as prose only.
- Impact: contaminated benchmark numbers (SB-1 caught by luck) and any future multi-lane day. The new EV-*/CQ-* GPU tickets (retrieval evals on the three new GT sets) are exactly the next concurrent-GPU scenario.
- Checklist dimension: error handling / observability.
- Proposed change: on acquire, `FileGpuLock` writes `pid stage utc-ts` to `<lock>.holder` (best-effort, deleted on release) and the timeout error reads it back ("held by pid 4242 stage 'embed' since 14:02"); `doctor.check_gpu_lock_free` prints the same. In `app/retrieval_eval.py` (not protected) count questions whose error is a lock timeout and fail the report header ("N questions errored; run invalid") instead of scoring them as misses. A scheduler is not needed; the holder file is the smallest step. Reuse `FileGpuLock` (not in `ci/` protected scope; `rag/gpu_lock.py` has a sibling test).
- Needs: GPU no; foundation-protected no; operator sign-off no; re-embed no.
- How to verify: unit test: two `FileGpuLock`s on one path, second with `timeout=0.1` raises TransientError containing the first's stage label; eval harness test with a stubbed lock timeout yields a non-zero exit/`invalid` flag.
