# RV-2 — parsing, chunking and book structure

Scope: `rag/parser.py`, `rag/chunker.py`, `rag/book_summarizer.py`, `rag/summarizer.py` (chunk/block consumption), `app/rechunk.py`, `app/ingest_local.py`, `contracts/provenance.py`, `contracts/parser.py`. Read-only review; corpora opened `mode=ro`; my probe scripts live in the session scratchpad (not committed). All counts below were produced by me unless attributed to a named artifact.

## Summary
1. One function pair, `_heading_depth` + `_SectionTracker` (`rag/parser.py:457-494`, fed by the unfiltered `text_level >= 2` test at `:539`), is the root cause of most structure defects: flat books, running headers/NOTE lines/R output as path roots, stale "term > 3.6" clause numbers, lost chapters. Chunk boundaries are run-lengths of `section_path`, so path defects become chunk defects. It has no unit test, and it can be re-run on CPU from stored blocks.
2. Two chunkers coexist and nothing records which produced a chunk. VERIFIED: all 119 standards documents reproduce byte-for-byte under the new bounded chunker; 299 of 300 sampled main papers reproduce byte-for-byte under the old 1,500-word chunker. `rag_fix_ids.txt` is a re-chunk list for pre-fix ingests, not a version marker. A main re-chunk is about 3.4x chunks (about 1.35M embeds) and breaks every positional chunk id and first-block-anchored gold in the fixtures.
3. The structure information needed to fix most of this was thrown away at parse time. Main keeps no `content_list.json`, no table HTML and no `text_level`, and its `tables`/`figures` tables are empty. Standards kept 121 `content_list.json` files by accident of RI-18. Stubs (9.1% main, 6.95% standards) are mainly emitted by the chunker for headings the parser kept: about a quarter are "References" headings whose bibliography was diverted to GROBID, and GROBID's output is then not persisted (`rag/document_store.py:468`).

## Findings

### F-2.1 `_SectionTracker` is the single root cause of D2, D3, D4 and D5, and it is untested (severity: critical)
- Evidence [VERIFIED]: `rag/parser.py:539` treats every `text` item with `text_level >= 2` as a heading, with no length, sentence, repetition or position filter. `_heading_depth` (`:457-472`) returns depth 1 for any un-numbered text and the digit count otherwise; `update` (`:490-494`) pops everything at depth >= the new one. I ran the tracker on real shapes:
  - `3 Terms and definitions, 3.5, ASIL decomposition, 3.6, audit` gives `'ASIL decomposition > 3.6'` then `'audit'`. This is Author A's "section ASIL decomposition > 3.4 is just '3.4'", reproduced exactly.
  - `Chapter 4, The Bias Equation, Confounding, Chapter 5, T-Learner` gives each as a depth-1 root, so there is no chapter level (Authors I, J, H).
  - `FOR UL INTERNAL REFERENCE` then `6.4.1.2 Risk` gives `'FOR UL INTERNAL REFERENCE > 6.4.1.2 Risk'`. A `NOTE 1 ...:` line then `4.3 Next` gives `'NOTE 1 ...: > 4.3 Next'`, and `## [1] 120` then `5.3 After` gives `'## [1] 120 > 5.3 After'`. These are the "X > 4.3 ..." and R-output patterns in the logs of Authors A, C, D and H.
  - The numbering check is purely arithmetic: `4.3` nests under whatever depth-1 text is on the stack, even if it is not `4 ...`.
  - `rag/test_parser.py` has no test of `_SectionTracker`/`_heading_depth`; every `content_list` fixture there uses `text_level: 0` (lines 258, 389). The most defect-generating function in the pipeline has no spec.
  - Propagation: the chunker groups by `section_path` run-length (`rag/chunker.py:224`), so every path error becomes a chunk boundary or a wrong label. `book_summarizer._heading_groups` (`rag/book_summarizer.py:125`) groups the same way and carries its own compensating heuristics (marker regexes, sequence checks, title scoring, `:35-90`).
  - The `ponytail:` note in `_heading_depth` records this ceiling and names the upgrade path (outline/font hierarchy). The ceiling has been reached.
- Impact: every section-path-dependent consumer is affected (chunk text prefix, citations, `gold_chapter_title`, chapter routing). The GT authors killed or fixed 27 of 30 Author-I chapter labels and 3 of 15 Author-J labels (causal-books crossverify) because paths were not chapters. It affects every book and every standard, and about 31-44% of papers have nested paths whose correctness is unknown.
- Checklist dimension: 1 (unknown unknowns), 3 (the "authoritative" path is derived by one heuristic with no check), 5 (programming by coincidence).
- Proposed change: replace the tracker's decision rules, keep its interface.
  1. A numbered heading nests only under a stack entry whose number is its numeric prefix; otherwise it replaces the stack from the matching ancestor (or root).
  2. Treat as non-headings: text ending in `:`, text over about 120 chars or containing sentence punctuation, `NOTE n`/`Note:`, text starting `#`/`[`/`http`, text whose only content is a number.
  3. For definitions clauses, make a bare `N.N` heading a pending marker attached to the next heading rather than a push.
  4. Add golden tests from the four shapes above (all four are executable as written).
  5. Apply the same function over stored blocks to rewrite `blocks.section_path` for existing corpora. A heading block is identifiable as `norm(text) == last component of section_path` (the chunker already relies on this at `rag/chunker.py:250-251`); where `_merge_tiny_headings` has the block, so does a post-pass.
  Files: `rag/parser.py` (tracker), `rag/test_parser.py`, a new one-shot `app/restructure.py` modelled on `app/rechunk.py` (which can already walk papers and write via `DocumentStore.put`).
- Needs: GPU no (tracker is pure; standards re-run from retained `content_list.json`, main from blocks); foundation-protected path: `DATA-CONTRACTS.md` says `Block.section_path` is "assigned once by the Parser... never re-derived", so a post-parse rewrite of stored blocks needs operator sign-off on that wording (a `parser_id`/`structure_version` field would make it legitimate); re-embed yes for chunks whose text changes (all paths with changed prefix).
- How to verify: new unit tests pass; then on the 119 standards documents and the five main books, recompute paths and report (a) number of chunks whose root is a number-only or `NOTE`/`#`-prefixed string (target 0), (b) distinct roots for the three flat books (target: collapses to about chapter count), (c) UL 4600 root count (target: no root equal to the watermark).

### F-2.2 Two chunkers coexist and there is no chunker version anywhere (severity: high)
- Evidence [VERIFIED]: I wrote the pre-8301342 chunker to scratch (`git show 8301342^:rag/chunker.py`) and ran both chunkers over the stored `blocks` of every standards document and a random 300 main papers, comparing to stored `chunks.text`:
  - standards: 119 of 119 equal the NEW chunker (52 of the 53 `rag_fix_ids.txt` ids plus the 67 ingested 2026-11-02/03; the 53rd id `local:c1c1e343f734` was swapped out of the config). `ingest_state` dates show the 52 listed ids were ingested 10-27 (31) or 11-01 (21), before commit 8301342 (2026-11-01 09:49); `rag_fix_ids.txt` is dated 09:47. So it is the list of pre-fix documents that were re-chunked, and the other 67 were ingested with the new code. The whole standards corpus is new-chunker: 35,714 chunks (the old chunker would give 17,767 on the same blocks, 2.0x).
  - main: 299 of 300 equal the OLD chunker (the one `neither` is probably a pre-T-DOC62 duplicate-heading paper, not investigated). New chunker on the same 400-paper sample: 12,423 to 41,943 chunks (3.4x), p95 length 6,635 to 1,405 chars, chunks over 8,000 chars 268 to 0, stub chunks 1,286 (10.4%) to 2,748 (6.6%), total characters +12.5%.
  - `grep -rn chunker_version` over `*.py/*.sql/*.md` returns nothing (VERIFIED): `chunks`, the Qdrant payload and `Chunk` carry no algorithm tag. `rag/chunker.py:23-27` constants are deliberately "not Config fields". `child_parent_expansion` (a misleading name, see DATA-CONTRACTS "Provenance & structure") also gates bounding and `_merge_tiny_headings`.
  - DATA-CONTRACTS IDs spine promises "rebuilding the derived stores reproduces the same references (ADR-04)". That is false across chunker versions, because `chunk_id = {paper_id}:c{index}` (`rag/chunker.py:386`).
- Impact: any cross-corpus comparison (main vs standards: recall, stub rate, truncation, ligature rate) confounds corpus with chunker. The 3 new GT sets mix both: standards GT (128) and its 10 books are new-chunker; causal-books GT (74) and paper-passage GT (61) are old-chunker; the Waymo fixtures are old. Running the same pipeline on the three GT sets compares unlike chunk granularities (about 900 vs about 1,900-char median, p95 1,400 vs 6,600). Any ingestion into main from this branch silently adds new-chunker papers to an old-chunker collection.
- Checklist dimension: 3 (information leakage: one decision, chunk granularity, implicit in data), 4 (DRY/reversibility), 7 (undocumented rationale: the 220/1,200 constants have no recorded measurement).
- Proposed change: stamp, do not migrate. Add `chunker_id` (e.g. `bounded-v2`) to the vector payload (`rag/orchestrator.py::vector_payload`) and a column on `chunks`; backfill by running the comparison I did (it is about 20 lines over `blocks`/`chunks`). Record the finding in `docs/` so evaluation reports state which chunker each corpus used. Do NOT re-chunk main just to get comparability: see F-2.3 for what a re-chunk costs and buys.
- Needs: GPU no; foundation-protected: `contracts/chunker.py` is frozen, so use payload and a migration, not a field on `Chunk`; operator sign-off yes (schema column); re-embed no (payload-only, uses the CQ-2 payload-update method).
- How to verify: `SELECT chunker_id, count(*)` per corpus equals {standards: bounded-v2 119 docs, main: legacy-1500w 12,390}; a test asserts `Chunker.chunker_id` appears in every payload.

### F-2.3 Re-chunking main is a 1.35M-embedding job whose benefit is mostly the oversize/truncation fix; `rechunk.py` also re-embeds unchanged chunks (severity: high)
- Evidence: [INFERRED from the 400-paper sample] 399,676 x 3.4 gives about 1.35M chunks, about 13.8 GB of 2,560-d float32 vectors versus 4.1 GB now. [VERIFIED] `app/rechunk.py:189` embeds `[c.text for c in new_chunks]`, every chunk of a changed paper, and `:188` deletes only `old_ids - new_ids`. With positional ids a single removed stub shifts every later `c{n}`, so id diffing is useless as a change detector; there is no comparison on text. A text-only change (ligature/`<sub>` normalization) leaves ids stable but `:161` equality then fails for the whole paper and re-embeds all of it.
- Impact: the cheap, valuable part of the chunker change is bounding (3,138 main chunks are truncated at 4,096 tokens per the embed-truncation report; 16.3M of 1,080M chars, 1.51%). The embed-truncation report already proposes re-chunking only the oversized chunks (option 1). With positional ids that is awkward: re-chunking a section splits one chunk into 3-5 and shifts all later ids in the paper (so every paper with an oversized chunk, about 80 papers with 30k+ char chunks and about 2,000+ with any, re-embeds whole). A full re-chunk also changes which block is first in a chunk, so every `gold_block_id`/`gold_chunk_id` in `fixtures/eval/*.json` (about 700 chunk-id references in 11 files, counted by regex) and in the three GT sets goes stale (the GT sets keep verbatim excerpts, and `excerpt_block_id` exists in `eval_book_questions.json`, so they are remappable; the fixtures that score on first-block anchor are not).
- Checklist dimension: 3, 4 (reversibility: ids encode the algorithm).
- Proposed change, smallest first:
  1. In `run_rechunk`, build `old_by_id`, embed only chunks whose `text` differs, upsert only those, delete `old_ids - new_ids` (needs to read old vectors: no; payload re-upsert is cheap). This is about 10 lines, reusing the existing `vector_payload`.
  2. Make chunk ids content-addressed from the anchor block: `{paper_id}:{first_block_index}:{k}` (k = split ordinal within the block-run). This costs a one-time fixture rewrite but makes every future chunker change local: unchanged chunks keep id and vector. Reuse `Chunk.parent_id` (already the first block id).
  3. Do the targeted bounded re-chunk on the 2,500-3,100 oversized-chunk papers first (list from `scripts/truncation_census.py` or `2026-11-10-embed-truncation/measure.py`) rather than all 12,390.
- Needs: GPU yes (re-embed; counts above); foundation-protected: `DATA-CONTRACTS.md` IDs spine is a frozen contract, so step 2 needs operator sign-off; step 1 and 3 do not; re-embed yes.
- How to verify: dry run (`python -m app.rechunk --dry-run --paper-ids-file ...`) on the oversized-papers list reports `new_chunk_count` and the number of changed texts; pass criterion: re-embedded count equals the number of changed chunk texts (after step 1), not the paper's total.

### F-2.4 Raw parser structure is discarded for main; blocks carry no heading flag, table HTML or typed furniture (severity: high)
- Evidence [VERIFIED]: standards `blobs/figures/*/auto/` hold 121 `*_content_list.json` (53 MB total) plus `_content_list_v2.json` and `_middle.json` (1.5 GB with images). Main `blobs/` holds 12,390 `.md` files only (0 `content_list.json`); `tables` and `figures` tables have 0 rows in main (2,189 and 3,544 in standards). RI-18 (figures/tables capture) postdates the main ingest. PRD ADR-13's own argument ("re-parsing the whole backlog later to recover figures would be the expensive, lossy path") applies equally to heading levels, table HTML and furniture typing. Standards `content_list` shows what is available: text levels only 1 (625) and 2 (17,622); typed `header` 9,479, `footer` 3,903, `page_number` 10,541 (all skipped by `_SKIP_TYPES` at `:156`); the v2 file also types 403 `index` items (TOC/index) that the v1 file the adapter reads does not distinguish. Main PDFs are in `pdf_cache` (31 GB, 21,006 files), so re-parse of main is GPU-only, never a re-download.
- Impact: for standards (119 documents) D3-D6 and part of D10 are fixable on CPU without touching MinerU. For main the same fixes work only to the extent that stored blocks (text, type, page, bbox, section_path) carry the signal (F-2.5, F-2.7 show they do for furniture, stubs and front/back matter, but not for table spans or text_level). Any future parse still loses it unless persisted.
- Checklist dimension: 4 (reversibility: re-parse cost is the lock-in), 7 (rationale for ADR-13 not generalised).
- Proposed change: keep each parse's `_content_list.json` and `_middle.json` (small: about 0.44 MB/document; about 5.5 GB for 12.4k, INFERRED) in `blob_dir` alongside the `.md` blob, and store the table HTML in `tables`. No new code path: `rag/parser.py::_read_mineru_output` already reads them from `workdir/{stem}/auto/`; the only requirement is that `output_dir` is durable (as `_PdfDownloadParser` already makes it for figures, per the `output_dir` bullet in the module docstring) and is not cleaned up. Make the standards copy the template.
- Needs: GPU no for the persistence change; yes for any main re-parse; foundation-protected: `rag/parser.py` module is adapter-level, `contracts/parser.py` unchanged; operator sign-off for disk; re-embed no.
- How to verify: after any ingest run, `find blobs -name '*_content_list.json' | wc -l` equals the number of documents ingested in the run.

### F-2.5 Running furniture promoted to headings is a standards-corpus problem and is detectable positionally from stored blocks (severity: high)
- Evidence [VERIFIED by probe]: blocks with identical normalized text (under 150 chars) on 4 or more distinct pages at the same y-position (12-pt buckets, at least 70% of occurrences): standards 20 of 119 documents; 947 blocks; 1,678 chunks (4.7%) have such a string as their `section_path` root. Top hits: UL 4600 "FOR UL INTERNAL REFERENCE OR CSDS USE ONLY - NOT FOR OUTSIDE DISTRIBUTION" (215 blocks), PAS 8800 `ISO/PAS8800:2024(en)` (96), FAA System Safety Handbook chapter running heads (about 140 across variants), NASA SP-2010-576 page head (17). In main only 66 of 12,355 documents and 150 root chunks (mostly `<sub>`-broken "continued" lines, journal names, "Manuscript submitted to ACM"). This matches the GT logs (Authors B, C, E: "about 196+ chunks", "every chunk carries a stale running header"; D: NASA SE Handbook, Rausand, RAND). Of the cause, MinerU did type 9,479 headers and 3,903 footers correctly (skipped at `:156`); the ones that reach the tracker are the ones its layout model mis-typed as `text` with `text_level 2`.
- Impact: UL 4600 (1,384 chunks) has a path that is wrong for most clauses, so clause-by-section retrieval and the `FOR UL...` string appear in about 200 chunk prefixes (it is also embedded: `chunk.text = title\nsection_path\n\n...`, `rag/chunker.py:376`, so it is a lexical and dense feature in every affected chunk). Documents of this class are the standards corpus's primary content (regulations, handbooks).
- Checklist dimension: 3.
- Proposed change: one pre-pass in `_build_blocks` over `content_list` (standards: retained file; new parses): count `(normalized text with digits collapsed, round(y0/12))` per page; any `text` item whose key occurs on at least 4 pages is treated as furniture and skipped before `section.update`. For existing corpora, apply the same key to stored blocks and re-run the F-2.1 tracker. No existing function does this (`_strip_duplicate_heading` handles only exact text-equals-path duplicates inside a chunk); `app/exp_*` has none.
- Needs: GPU no; foundation-protected no; re-embed yes for the 1,678 chunks and any chunk whose merged boundaries change (one standards re-chunk, about 35k embeds).
- How to verify: rerun my positional probe after the change; target 0 furniture roots in standards; UL 4600 `distinct(section_path root)` no longer includes the watermark; spot-check that real template headings (e.g. "Validation Method" x61 pages in `local:7c89760c33e1`) are not removed (they repeat with different y; the y-clustering criterion is what separates them: if it removes them, the 70% threshold needs raising).

### F-2.6 Stub chunks: chunker-created, mostly avoidable, and the new chunker does not reduce them in absolute terms (severity: high)
- Evidence [VERIFIED by probe, body under 60 chars]: main 37,770 (census at its threshold: 36,364), standards 2,825 (census: 2,483, 6.95%, 400 bare-number). Composition in main: empty-body headings 94%: 36.6% followed by a non-child section ("APPENDIX"), 28.2% a parent followed by its first child heading, about 25% "References/Index/Contents" headings (4,548 + 4,503 + 510 + others), 4.6% heading-duplicate bodies; standards: 24% empty next-other, 28% parent heading before child heading (15.5% duplicate-body plus 12.5% empty), 14.2% bare clause number. On the 400-paper main sample, re-chunking with the new code produces 2,748 stubs against 1,286 stored; the share falls (10.4% to 6.6%) but the count doubles.
- Mechanism [VERIFIED]: `_build_chunk` emits `title\nsection_path\n\n` plus `_strip_duplicate_heading(...)`, which turns a heading-only group's body into `""` (`rag/chunker.py:169-173`, `:370`). `_merge_tiny_headings` merges only when `same_parent` (both paths contain ` > ` with equal parents; a depth-1 parent heading never qualifies) or inside a terms-and-definitions clause (`:269-276`). A bare clause number is intentionally left as its own stub when the following term group is not heading-only (`:261-266`), so `"fault tolerance > 3.61"` with body `3.61` is emitted by design. References: `parser.py:545-552` diverts `ref_text` lists to GROBID but leaves the "References" heading as a block, so about 9.8k main chunks are an empty "References" chunk (23 of 30 Author-G papers).
- Impact: 7-10% of every corpus's index points at empty text; these vectors are nearest neighbours of generic queries (CQ-3 filters them at query time; that treats the symptom and the vectors still sit in Qdrant). Worse, 400 standards stubs and the stale-number pattern mislead number-based queries (Author A: "what is 3.6?" mis-maps).
- Checklist dimension: 2 (shallow chunk), 5 (limping on instead of dropping).
- Proposed change: in `_group_blocks`/`_split_oversized`, do not emit a group that is only its own heading text: carry it as a prefix of the following group's body (its `section_path` already prefixes the following chunks, so the child chunk already contains it: zero information is lost) or drop the group when nothing follows. For bare clause numbers: prepend the number to the next term group's derived first block (`model_copy`, like `_table_parts` does), so the chunk reads `3.61 fault tolerance time interval ...`, and drop the stub. Files: `rag/chunker.py`, tests next to `test_complete_definition_retains_its_term_path_after_a_stale_numeric_marker` (`rag/test_chunker.py:615`), which currently asserts the stub-preserving behaviour and would change. Reuse: `scripts/chunk_quality_census.py --stub-ids-out` as the before/after check.
- Needs: GPU yes only for the re-embed (positional-id shift means every chunk after a removed stub in the paper re-embeds unless F-2.3 step 2 is done first); foundation-protected no; operator: one decision on whether the number belongs in the term chunk.
- How to verify: `python scripts/chunk_quality_census.py <db>` on a re-chunked copy: standards stub rate under 2%, `bare_number` 0; sample 10 definitions in ISO 26262-1 and confirm the number sits in the term's chunk.

### F-2.7 Front/back matter can be classified from blocks on CPU; the repo already has three partial detectors that do not share code (severity: medium)
- Evidence [VERIFIED]: label-root chunks: main References 12,041 (3.0%, 9.5M chars), Acknowledg* about 5,000, Contents 598, List of figures/tables 81, Bibliography 123; standards References 553, Contents 361, Foreword 107, Preface 93. Label matching misses books, where roots are junk: TOC-line density (at least 8 lines, 60% ending in page numbers or dot leaders) finds 63 main-book and 94 standards-book TOC chunks, still an undercount (GT logs: Elements c1 3,147 chars, c158 Bibliography, c159 Index 6,701 chars; Causal Inference in Python c4 9.7k TOC and c333-354 single-letter glossary/index; Trustworthy c214 has the index glued on at 11,068 chars). `rag/summarizer.py:106-109` cuts a paper at the first `# references|bibliography|appendix|supplementary` markdown heading (so an early "Supplementary" heading discards the rest); `rag/book_summarizer.py:271-279` detects front matter by word count; `chunk_quality_census.py` detects stubs. Three partial detectors, none in the chunker.
- Impact: index/TOC chunks match many queries lexically (Author A: "propensity score" hits in contents; TS 5083 "clause title" questions can hit only the TOC chunk); reference lists (about 2.4k main chunks with content) rank for author-name queries; the summarizer's regex is a second, divergent rule.
- Checklist dimension: 4 (DRY: the knowledge "what is back matter" is in two places), 3.
- Proposed change: one classifier `block_role(blocks) -> {front|toc|index|refs|ack|body}` in `rag/chunker.py` (or a sibling), from the signals already in `Block`: root heading label regex, TOC-line density, page-position (first 3% / last 5% of pages), single-letter title runs, dot-leader lines. Write the role into the payload (like CQ-5's category tags) and let CQ-3's stub filter read it; do not drop the blocks (grounding, ADR-06). Have the summarizer call the same classifier instead of its regex. Reuse: `scripts/chunk_quality_census.py` for validation and `rag/book_summarizer._FRONT_MATTER_MAX_WORDS` logic.
- Needs: GPU no; foundation-protected no; re-embed no (payload tag; excluded at query time) unless chunks are also dropped.

### F-2.8 `_normalize_text` and `_merge_tiny_headings` are tuned to ISO 26262 and are either dead or partially harmful outside it (severity: medium)
- Evidence [VERIFIED]: `rag/chunker.py:40-51` is a 10-entry dictionary of glued words, all from ISO 26262-3 severity/controllability tables ("moderateinjuries", "Simplycontrollable", ...). Probe over all blocks: standards 23 hits in 106,202 blocks, main sample 0. The classes it cannot touch are the ones the logs name: "oroccupational", "reversiblesignificant", "Extremelyremote" (MIL-STD-882E/FAA), "faultsand", "residualrisk", "quantitativetargets" (PAS 8800), "successcriteria", "aredefined" (NASA). The glued-word proxy finds 853 standards chunks (2.4%). The two generic regexes (`:57-58`) fire on 1,386 standards blocks (1.3%) and 151 main-sample blocks (0.2%), and damage identifiers: `a<sub>max,brake</sub>` becomes `a<sub>max, brake</sub>` (RSS parameter names in standards), citation lists `2016a,b` become `2016a, b`, and `(?<=[a-z])\.(?=[A-Z][a-z])` rewrites dotted names such as `Foo.Bar` and some URLs. The `[SEC]O` to `[SEC]0` rewrite (`:59-69`) and the `ASIL`/`[SEC][0-9]` header detection in `_table_parts` (`:111-115`) are ISO 26262 HARA specific. `_merge_tiny_headings` hard-codes clause 3 as "Terms and definitions" (`:243-246`, `^3\s`, `3\.\d+`), true for ISO 26262/21448/21434/PAS 8800 but not for SAE, EU regulations or the 10 books.
- Impact: low for harm (0.2% of main blocks, text is derived-only; raw blocks and `Anchor.snippet` are untouched; one unrecorded side effect: GT excerpts for standards were authored against normalized text, so a future change to these rules can invalidate verbatim excerpts); the larger risk is the false sense that glued words are handled. A dictionary cannot scale to the defect and it ties the generic chunker to one standard.
- Checklist dimension: 3 (information leakage: ISO 26262 vocabulary in generic code), 6 (consistency: comment says "conservative", behaviour is corpus-specific).
- Proposed change: (a) restrict the two regexes to skip `<sub>/<sup>` spans and `\d[a-z],[a-z]` citation patterns (add them to the `protected` regex at `:37`); (b) move the 10-word dictionary and the `SO/EO/CO` and `ASIL` rules into a per-corpus normalization table keyed by `paper_id` prefix or by a `corpus_profile`, or delete them and accept the 23 blocks; (c) treat glued words as a parse-quality tag (F-2.7 payload) rather than a repair, since fusion needs a language model or dictionary-segmentation (e.g. a wordfreq-style segmenter), which is a new dependency: skip unless the standards GT run shows lexical misses on them.
- Needs: GPU no; foundation-protected no; re-embed yes for blocks whose derived text changes (small: 1.3% of standards blocks).
- How to verify: diff derived text before/after over the standards blocks: changes limited to the 23 dictionary blocks plus prose-only commas; no change inside `<sub>`.

- Checklist dimension: 3, 4.
- Proposed change: if CQ-1's sparse-arm repair is built from a restoration function (dropped `ff/fi/fl/ffi/ffl` after a known-word check), expose that function and call it from `rag/chunker.py::_normalize_text` too, in one place; keep CQ-1's measurement (sparse-only) as the first A/B arm, the second arm being repaired chunk text. ### F-2.10 Table conversion loses structure at `markdownify`, and the raw HTML is not kept for main (severity: medium)
- Evidence [VERIFIED]: `rag/parser.py:572` `markdownify.markdownify(html)`. I ran it on a rowspan/colspan/superscript fragment: `rowspan` content appears only in the first row so later rows' cells shift left; `<sup>-8</sup>` becomes `-8` giving `<10-8 h-1` (Author A's ISO 26262-5 PMHF case); `markdownify`'s `sup_symbol='^'`/`sub_symbol='_'` options exist in the installed version and produce `<10^-8^ h^-1^`. Fused words are not introduced by `markdownify` (`<br>` becomes a space, verified), so "oroccupational" is MinerU's cell text (INFERRED). Notes/footnotes split into separate chunks and header rows lost (Authors A, B) are chunker behaviour on the flattened text (`_table_parts` repeats caption and header but cannot recover spans).
- Impact: wrong numbers in table cells are the worst kind of retrieval error (a row's value attached to the wrong column); 2,189 tables in standards (3 of 8 GT table-requirement answers touch lost spans), 147/1,430 (10%) of GT-sampled paper chunks contain markdown tables.
- Checklist dimension: 5 (error to defined-away: do not emit columns that are wrong).
- Proposed change: pass `sup_symbol`/`sub_symbol`; expand rowspan/colspan with BeautifulSoup (a transitive dependency of `markdownify`; about 25 lines) before conversion; if the span structure is irregular, fall back to the HTML text of the row as `col: value` lines. Standards: rebuild from retained `content_list.json` (CPU). Main: no HTML stored, so only new parses or an explicit GPU re-parse of table-heavy documents benefit; `tables` already stores markdown only, so add a `html` column when persisting (F-2.4).

## Stored-blocks sufficiency (asked)
Sufficient to re-derive on CPU, VERIFIED by running the old and new chunkers and my probes over `blocks`: chunks (byte-identical reproduction, F-2.2), heading blocks (text equals last path component), furniture (page + bbox + text), stubs, front/back matter (type, page, density), section paths (re-running the tracker on heading-flagged blocks), `<sub>` normalization. Not sufficient: table cell spans and HTML, `text_level`, mis-typed `header`/`footer` items (already dropped), OCR/ligature repair beyond dictionaries, `index` items that MinerU v2 types, and anything involving figures. For standards the retained `content_list` closes all of those; for main only a re-parse does. ## Things that are good and should not be changed
1. Raw blocks and `Anchor.snippet` are never rewritten; all normalization is on derived chunk text (`rag/chunker.py:30-36`, `:370`). This keeps grounding re-verifiable (`get_span`) and makes every fix above reversible.
2. `app/rechunk.py` is correct and reusable: SQLite commits before the vector delete/upsert, deletes only vanished ids, skips no-ops, has `--dry-run`, and uses the shared `vector_payload` builder (RI-3). It needs only the "embed changed text only" change in F-2.3.
3. `_table_parts` never drops a row, repeats caption and header, and bounds oversize rows (`rag/chunker.py:92-146`); the new chunker turned 8,487 oversized main chunks into 0 on the sample.
4. `scripts/chunk_quality_census.py` and the embed-truncation and ligature censuses are read-only instruments with tests; use them as the before/after gates.
5. The MinerU adapter's grounding rule (never fake a bbox, skip degenerate blocks, page-monotone output: 0 backward page jumps in 12,509 documents) holds; the parser is not the place to spend a swap (ADR-06 stands; `PARSER-ALTERNATIVES-EVAL.md` is about GPU utilisation).
