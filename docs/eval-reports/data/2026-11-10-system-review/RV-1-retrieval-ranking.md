# RV-1 — retrieval and ranking (retriever, vector index, reranker, embedder, composition root)

Scope read: `rag/retriever.py`, `rag/vector_index.py`, `rag/reranker.py`, `rag/embedder.py`, `app/assembly.py`,
`contracts/{retriever,vector_index,fusion}.py`, `rag/fakes/fake_{vector_store,reranker,embedder}.py`, the four tests
files, the live Qdrant segment metadata (read-only, files on disk; the service is down), the five `config.yaml`
files, and the evaluation reports named in the brief. Scratch scripts for the two measurements I ran are in the
session scratchpad (`rv1_auc.py`, `rv1_tok.py`); both are CPU-only and open SQLite with `mode=ro`.

## Summary
1. The score returned with every result is the RRF fusion score (rank-derived, ceiling 1/61), not the reranker score; the reranker's scores are thrown away. So the "no relevance floor until a score census separates answerable from absent" gate (RI-M7) was tested on a signal that cannot separate by construction, and nothing in the pipeline carries a relevance signal that could keep results on topic (F-1.1, F-1.4).
2. No live Qdrant collection has a payload index (`indexed_fields: {}` in every segment), yet every query is filtered (`kind` is always set). Filtered ANN search on unindexed fields is the most likely silent recall loss in the pipeline, especially for `paper_id`, `author_org`, `doc_type=book` and the summary path (F-1.2).
3. The new chunker emits several chunks that share one anchor block (standards: 2,661 of 35,714 chunks, 7.5%; main: 0). That breaks the pending member-block derivation as designed (it assumes unique anchors), makes "anchor-block equality" unable to tell fragments apart, and makes citation snippets point at the block start rather than the fragment (F-1.3).
4. The per-corpus lever question is unsettled in both directions: Waymo's own numbers show pool 128 losing 4 of 65 papers, and "sparse hurts on Waymo" is a one-question effect with the sign flipping between fixtures. The experiment already half-exists (`run_baseline.sh`); it needs a pre-registered decision rule and a weight axis (F-1.5).

## Findings

### F-1.1 The score returned to callers is the RRF score; reranker scores are discarded, and the RI-M7 "no floor" decision rested on that signal (severity: high)
- Evidence: `rag/retriever.py:219` `scores = {hit.id: hit.score ...}` (fused RRF) and `:275` `score=scores[candidate.id]`; `TeiReranker.rerank()` (`rag/reranker.py:220-232`) sorts by score then returns bare `RerankCandidate` objects, dropping the score; `RerankCandidate` has no score field (`contracts/retriever.py`). So order = reranker, `score` = RRF, and they disagree. The census in NB-X-F reports top scores of known-absent queries in [0.0082, 0.0164] and answerable ones overlapping; 0.0164 = 0.5/61 + 0.5/61 = the RRF ceiling, so these are RRF values (the report calls them "fused/reranked"). The `McpServer.semantic_search` docstring rejects a relevance floor "until a score-distribution census ... shows the two distributions actually separate"; the census it cites measured RRF, which is rank arithmetic and carries no absolute relevance. [VERIFIED]
- Impact: every consumer (agent, dashboard) sees a number that looks like confidence and is not; abstention ("the corpus does not answer this") and any topic-focus floor are impossible to build or even to evaluate today. Affects all five corpora on every query.
- Checklist dimension: 5 (correctness posture / contract: `score` meaning) and 3 (information hiding gone too far: the one absolute signal is hidden inside the adapter).
- Proposed change: smallest step with no contract edit: an experiment-only recording subclass of `TeiReranker` (wrap `rerank`, keep `[(id, score)]`) used by `app/retrieval_eval.py` to re-run the RI-M7 census (answerable vs known-absent, plus the off-topic focus set) on reranker scores. If the distributions separate, then (and only then) propose `RerankCandidate.score: float | None = None` plus `GroundedResult.score` = reranker score via the T-F7 path. Reuse `retrieval_eval.top_score` plumbing (`QuestionResult.top_score`).
- Needs: GPU yes (reranker); foundation/sign-off only for the later contract step (`contracts/retriever.py`); re-embed no.
- How to verify: on the 26 known-absent + 150 answerable questions of the Waymo fixtures, compute AUC of reranker top-1 score for answerable vs absent. AUC >= 0.85 means a floor is viable; ~0.5 confirms RI-M7's conclusion on the right signal and closes the question.

### F-1.2 No payload indexes exist on any live collection, and every query is filtered (severity: high on impact if confirmed, INFERRED)
- Evidence: every `payload_index/config.json` under `.phase0-data/qdrant/collections/{papers,av_standards,waymo_av_safety}/0/segments/*` contains `{"indexed_fields":{}}` (8, 7, 8 segments). `rg 'create_payload_index' rag app` has no hits; `_ensure_collection` (`rag/vector_index.py:~190`) creates none. `Retriever._hybrid_hits` always sets `data["kind"]` (`rag/retriever.py:410`), so `kind` plus any of `doc_type`/`paper_id`/`categories`/`author_orgs`/`published` is an unindexed filter on a 400k-point HNSW. Filters are applied inside Qdrant on both arms (pre-filter, `_qdrant_filter`), so they do not starve the pool by design; the question is whether the dense arm's filtered graph traversal finds the matching points when the filter is selective (a single `paper_id` in 400k; `kind="summary"`, 3% of points, on the `search_papers` path; `doc_type="book"`, 5 of 12k documents). Qdrant cannot estimate cardinality without an index, so it cannot pick exact scan for selective filters. [VERIFIED for the missing indexes; INFERRED for the recall loss]
- Impact: scoped searches (`paper_id`, `author_org`, `doc_type=book`) and the whole `search_papers` path can return fewer or worse dense hits than the exact answer, silently; the sparse arm (posting lists, exact) partly masks it. The existing measured recalls were all produced under this configuration, so they are internally consistent but may understate the ceiling.
- Checklist dimension: 5 (silent degradation), 4 (broken window).
- Proposed change: `create_payload_index` for `kind`, `doc_type`, `paper_id`, `author_orgs`, `curated_author_orgs`, `categories` (keyword) and `published` (datetime) inside `VectorIndex._ensure_collection` and one idempotent `ensure_payload_indexes()` for existing collections. Test first on a clone made with `VectorIndex.clone_points_into` (exists). Touches `rag/vector_index.py` only.
- Needs: GPU no (Qdrant only, but the clone is large); foundation no; operator sign-off yes (it changes candidate sets on a live collection); re-embed no.
- How to verify: on a clone, for 100 scoped queries (50 `paper_id`, 25 `doc_type=book`, 25 summary-kind) run the same dense query with `exact=True` vs HNSW, with and without the index. Pass: HNSW@index overlap with exact >= 0.99 and strictly greater than overlap without the index; count of queries returning < k filtered hits drops to 0.

### F-1.3 The new chunker gives several chunks the same anchor block; this invalidates the pending member-block derivation and the anchor-equality metric on standards (severity: high for standards, none today for main/Waymo)
- Evidence: `rag/chunker.py::_split_oversized` expands one block into several fragments (`_bounded_parts`, `_table_parts`), all `model_copy` of the source block with the same `block_id`; `_build_chunk` anchors on `group[0].block_id`. Measured: `select count(*), count(distinct paper_id||json_extract(anchor_json,'$.block_id')) from chunks` gives standards 35,714 vs 33,053 distinct (2,661 chunks, 7.5%, share an anchor), main 399,676 vs 399,676 (no sharing). `docs/design-notes/2026-08-28-xc-member-citation-adoption.md` §4 derives membership as "anchor_idx[i] <= x < anchor_idx[i+1]" and NB-XC gate G3 requires unique anchors; neither holds for chunks built by this chunker. `anchor.snippet` comes from `source_first.text`, the start of the whole source block, not of the fragment that matched. [VERIFIED]
- Impact: (a) the member-block change, built as designed, returns empty or wrong spans for fragments, i.e. wrong citations exactly where the new chunker was used (every standards re-ingest and anything re-chunked later); (b) eval anchor-block equality credits any fragment of the gold block, including a fragment that does not contain the gold text, and cannot see two fragments of one block occupying two of the ten slots; (c) a user clicking the citation lands on the start of a long block while the quoted passage is the third fragment.
- Checklist dimension: 3 (information leakage: chunk geometry is decided in the chunker and re-derived by guesswork in the retriever), 5.
- Proposed change: keep Variant A (it needs no re-embed and no frozen file) but change the helper: for a run of consecutive chunks with equal anchor, the earlier fragments' members are `{anchor}` and only the last fragment owns the trailing blocks; score fragment chunks by text containment of the gold span (add this to `app/retrieval_eval.py`'s standards path, reuse `gt_tools.py` verification) in addition to block equality. Longer term, persist the exact member list at chunk time (the chunker knows it) once a contract change is acceptable; the derivation then disappears. Add a G3-style census (duplicate-anchor count per corpus) to the doctor/chunk-census instrument (`368ce55`).
- Needs: GPU no; foundation: the long-term form touches `contracts/chunker.py` (yes), the helper form no; re-embed no.
- How to verify: for every standards paper, assert the derived member sets partition the paper's block index range exactly once (no gap, no overlap), counting fragments; pass = 0 violations over 35,714 chunks. And measure how many standards GT items are hit only via a non-containing fragment (expect > 0 given 7.5% sharing).

### F-1.4 Topic focus: a usable relevance signal already exists and is not read; cheapest reversible path is a post-rerank, opt-in lever (severity: high for the main corpus)
- Evidence: `papers.relevance_score` (cosine of summary embedding to the topic query, `rag/orchestrator.py:684`) is non-null for all 12,385 main papers. Against the EV-1 labels (`2026-11-10-topic-labels/topic_labels.tsv`, 6,711 on / 4,630 off), AUC(on > off) = 0.923 (my run, `rv1_auc.py`). Medians 0.417 on, 0.256 off, 0.328 borderline. Operating points: threshold 0.2745 keeps 95% of on-topic and 42% of off-topic; 0.33 keeps 86% / 18%; 0.36 keeps 77% / 8.5%. The Retriever already fetches the paper record for every reranked hit (`rag/retriever.py:247` `record = self._document_store.get(chunk.paper_id)`), so the value is in hand at no extra cost; nothing reads it, and `Config.relevance_filter: Literal["off","embedding"]` is dead. PRD ADR-18 "Risks" already says a too-broad focus_area "may need a light relevance filter", so a relevance lever is inside the settled design. [VERIFIED for the numbers; INFERRED for retrieval effect]
- Options against ADR-18 (explicit levers) and §11A (no server-side query rewriting; a corpus-quality prior is not a rewrite):
  - A. Post-rerank demotion or filter in `Retriever.retrieve` using `record.relevance_score`, gated by a visible lever. Zero migration, instantly reversible, measurable on the EV focus set. Weakness: acts on the already-truncated pool (32), so it can starve (40% of a pool off-topic leaves ~19, still > k=10 in most cases); `Coverage.returned` vs `candidates` shows it. A hard threshold loses 5-14% of on-topic papers, so default to demotion (move below-floor results after in-floor results, never drop) or opt-in filter.
  - B. Write `relevance_score` into the Qdrant payload (CQ-2 adds payload-update methods: reuse them) plus a float payload index; filter inside Qdrant. No pool starvation, same lossy threshold, reversible by dropping the field. Do this only if A shows starvation.
  - C. Blend `rerank_rank` with relevance (soft). Needs a weight lever; X-O found rank-agreement blends monotonically worse than pure BGE ordering on Waymo, so blending against a prior has a poor track record here; lowest priority.
  - D. Collection split: duplicates index and cross-topic recall, not reversible cheaply, and the operator decided to keep the off-topic papers. Reject.
  - E. Already available today with no code: `SearchFilters.categories` (e.g. `stat.ME, econ.EM, stat.AP`): off-topic share is 1/76, 0/21, 0/12 there but cs.LG is 25 off / 43 on, so it also removes real causal-ML papers.
- Impact: 37.4% of main-corpus papers (and by extension a similar share of the chunks returned for generic queries) can enter any answer; the agent has no field to filter them by.
- Checklist dimension: 7 (requirement is "stay on focus", the existing lever is dead), 4.
- Proposed change: wire option A behind a lever. Smallest wiring: `Retriever.__init__(..., relevance_floor: float | None = None, relevance_mode: "demote" | "drop")`, passed from `config.relevance_filter` (existing Literal; map "embedding" to demote) in `app/assembly.py::build_mcp_server`; a numeric floor needs a new `Config` field (foundation, T-F7) because ADR-18 forbids a buried constant, so put the floor in `Config` or make it a per-call `SearchFilters.min_relevance` (agent-chosen, the most §11A-aligned form; also foundation). Evaluate on the EV focus set arms: off / demote@0.27 / drop@0.27 / drop@0.33, reporting off-topic share in top-10 and gold recall on the three new GT sets (pre-register that recall loss > 1 question on a GT set rejects the arm).
- Needs: GPU yes (to run); foundation yes for the Config or SearchFilters field; operator sign-off yes; re-embed no.
- How to verify: off-topic share in top-10 on the focus set falls from baseline by >= 50% relative with zero gold losses on papers-passage GT (61) and causal-books GT (74).

### F-1.5 Per-corpus lever divergence is unjustified in both directions; the settling experiment exists but lacks a decision rule and a weight axis (severity: medium-high)
- Evidence: configs: standards `rerank_depth: 128`, main/Motional/Waabi 32, Waymo 32 with `hybrid_dense_weight: 0.7`, all others 0.5 (`research-system-rag*/data/config.yaml`, `research-system-rag/waymo/data/config.yaml`). No comment or report records why standards is 128. Measurements: main 210-question set, pool 32 vs 50: Recall@10 0.976 -> 0.967, 2 lost / 0 gained (a sign test with 2 discordant pairs is not significant); Waymo verified-84 R@10 65 -> 64 -> 61 (of 68) across pools 32/64/128 (NB-X-O) with 11 gold blocks sinking at 64 (NB-X-P); GT-WMR is depth-invariant in the top 10. Weight: on ver84 w=1.0 gains 1 paper (65 -> 66), on GT-WMR w=1.0 loses 1 (68 -> 67), shipped 0.7 is the best of the three on one fixture and the worst on the other; each is a single flipped question. `run_baseline.sh` states "it hurt on Waymo's full set", which the later NB-X-F data reduces to one question (`Q-GTA-011`) plus the stale 08-23 count. [VERIFIED]
- What follows: (1) 128 on standards is an untested transplant; the Waymo evidence says deeper pools cost top-10 stability on a corpus with confusable neighbours, which standards (many editions and commentary documents) also has. (2) 0.7 for Waymo and 0.5 elsewhere are both unproven; the data does not support any claim that sparse "hurts". (3) Defaults for main/Motional/Waabi are measured only on the 210-question set at pool 50 vs 32 and never on weight. The evidence that the settings matter per corpus is weak; the evidence that they differ for a reason is absent.
- Single experiment: one paired factorial per corpus on its own ground truth, 2 x 3 = depth {32, 128} x dense weight {0.5, 0.7, 1.0}, five arms vs the shipped arm, using `app/retrieval_eval.py --dense-weight/--sparse-mode` and `run_baseline.sh` generalised (it already runs depth 128/32/64 and dense/sparse extremes for standards) with `analyze_run.py` and the paired-flip + jitter envelope from `scripts/nb_xp_deeppool_tables.py`. Pre-register: report paired flips (not rates); change a corpus default only if the candidate arm has net >= +3 questions, flips ratio >= 3:1, and the same sign on at least two of {that corpus GT, verified-84, GT-WMR}; otherwise set all corpora to the same default (32, 0.5) so the divergence stops being an uncontrolled variable. Sets: standards 128, causal books 74, papers passage 61, ver84 68, GT-WMR 70, 210-question set.
- Needs: GPU yes; foundation no (config values per corpus only); sign-off for any default change; re-embed no.
- How to verify: the output is the flip table itself; pass criterion is the rule above, stated before the run.

### F-1.6 The sparse arm is raw TF x IDF without length normalisation or TF saturation, and the tokenizer keeps punctuation; fix both in the single recompute (severity: medium)

Hash collisions are NOT a problem: 50 of 401,245 distinct main tokens (0.012%) collide in the 2^31-1 space, 12 of 136,708 in standards. Legacy main chunks are unbounded (8,487 chunks over 8,000 chars; max 710k, `embed-truncation/report.md`), so raw TF lets those chunks dominate the sparse arm for any term they mention often. [VERIFIED for tokens and collisions; INFERRED for the length-bias effect]
- Impact: the sparse arm under-matches roughly a tenth of real occurrences and over-favours very long chunks; this plausibly contributes to the unstable sparse-arm results above.
- Checklist dimension: 6 (docs claim BM25), 5.
- Proposed change: in CQ-1/CQ-2's one sparse recompute, also apply tf saturation and length normalisation at index time (`tf * (k1 + 1) / (tf + k1 * (1 - b + b * len / avglen))`, `avglen` a constant measured once per corpus) so no second recompute is needed; strip edge punctuation in the tokenizer; move the tokenizer into a small shared function used by both `VectorIndex` and `FakeVectorStore` (F-1.10). Pre-register an A/B on the three new GT sets before adopting; the tokenizer change alone (CQ-1 as scoped, "ligature repair in the sparse arm only") should not ship separately from the weighting change, to avoid two recomputes over 400k points.
- Needs: GPU yes for the A/B; foundation no; re-embed no (sparse recompute only); sign-off yes (changes every main query).

### F-1.9 Failure behaviour: no degraded mode, and the query path can block for minutes (severity: medium)
- Evidence: `TeiEmbedder`/`TeiReranker` acquire the GPU lock with `_DEFAULT_GPU_LOCK_TIMEOUT_S = 300.0` (`embedder.py:50`); `app/assembly.py` constructs both with 60 s HTTP clients (`:626, :634`) and does not override the lock timeout ("nothing does today", `embedder.py:47`); retries are 2 with 1 s, 2 s backoff. Worst case per call is roughly 300 s of lock wait plus 3 x 60 s of HTTP. `Retriever` does not catch `TransientError`; `McpServer` does not either. A transient failure in any one of embed, Qdrant (5 s, no retry), or rerank (4 sequential batches at depth 128, each holding the lock separately) fails the whole query, even though after a reranker failure the RRF order is already in hand. Precedent: the old reranker 413 "dropped the question outright on every run" (2026-08-19 report), a recall loss that looked like a corpus gap. Empty pool returns `([], candidate_count=0)`, which is correct. Partial batches: a mid-pool reranker batch failing after retries aborts the whole rerank rather than scoring the rest. [VERIFIED code; the 300 s figure is arithmetic on the constants]
- Impact: while a GPU job holds the lock (the current state of this machine) an agent's search hangs for up to five minutes, then errors; MCP clients usually time out first, so the agent sees an anonymous timeout while the server is still blocked.
- Checklist dimension: 5 (crash early vs limp on; here it neither fails fast nor degrades), 1.
- Proposed change: pass a short `gpu_lock_timeout` from `build_mcp_server` (query path only; ingest keeps its default), e.g. 15-30 s, with an actionable message ("GPU busy: ingest/other process holds the lock"). A reranker-failure fallback to RRF order is a behaviour change that must be flagged in the response (needs `Coverage` change, foundation) so do it only if the operator wants availability over rank quality; do not degrade silently.
- Needs: GPU no; foundation no for the timeout, yes for a degraded-mode flag; sign-off for the timeout value; re-embed no.
- How to verify: hold the lock from a second process; `semantic_search` must return the explicit error within the configured timeout (pass = elapsed < timeout + 2 s).

### F-1.11 Critique of the in-flight tickets (severity: medium; advice, not new work)
- CQ-1 + CQ-2: do them as one sparse recompute including length normalisation (F-1.6); otherwise a second full recompute and a second A/B are needed. CQ-2's payload-update methods should be written once as a general `set_payload_by_filter`/batched update so F-1.4 option B reuses them. [INFERRED from the ticket descriptions in the brief]
- CQ-3 (retrieval-time stub filter): where it runs matters. If it removes stubs after the pool is truncated to 32/128, the reranked pool silently shrinks and the A/B confounds stub removal with a smaller pool; either filter inside Qdrant via a payload flag (needs the same payload-update machinery) or over-fetch `pool / (1 - stub_rate)` and truncate after filtering. - Checklist dimension: 4, 7.
