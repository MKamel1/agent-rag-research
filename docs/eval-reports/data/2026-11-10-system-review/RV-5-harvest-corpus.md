# RV-5 — Harvesting and corpus hygiene (why 37% off-topic; how to govern a mixed corpus)

Method: read-only. Labels = `2026-11-10-topic-labels/topic_labels.tsv` (12,385 papers: on 6,711 / borderline 1,044 / off 4,630). DB opened `mode=ro`; no arXiv API calls; Qdrant is down so nothing embedding-based was recomputed. All analysis scripts are in the session scratchpad (`a1.py`..`a6.py`), not the repo.

## Summary
1. The contamination is not diffuse: 3,440 papers published 2026-06-01..07-30 are 81% off-topic (2,798 of the 4,630 off papers = 60%); everything published before 2026-06 is 20% off (and 14% for 2012-2026-05 excluding the pre-2012 tail). Only 8% of that cohort contains any focus phrase in title+abstract, vs 82% for 2026-01..05: the queries are code-correct phrase queries, so this is arXiv-API-side behaviour on the newest papers, which `freshest_first` always reaches first, and every future top-up will hit it again.
2. Nothing records which query pulled a paper, no topic label is stored, and the PRD §8 monitors (50-paper spot-check, query attribution) were never built; `relevance_score` is stored but is a single joined-query cosine (AUC 0.92 on-vs-off, median 0.417 / 0.328 / 0.256) that nothing reads.
3. Cheapest forward fix with zero change to the existing corpus: a lexical title+abstract gate on `PaperRef` inside `Harvester.harvest` (no GPU, runs before MinerU parse): "contains a focus phrase" gives precision 0.85 / recall 0.85, "contains causal*/counterfactual/treatment/..." gives 0.80 / 0.96. Plus a per-batch off-share stop-loss.
4. "Supply exhausted at ~12,333" is true only for the 33 literal phrases; on-topic arrivals are a flat ~100-130/month, so the real gap is on-topic papers that never contain a phrase (not measurable without the API).

## Findings

### F-5.1 The off-topic mass is a recency artefact of the harvest, not a property of the query set  (severity: high)
- Evidence [VERIFIED from DB+labels]: off-share by publication month is flat 8-20% from 2024-02 to 2026-05, then 2026-06 = 83% (n=2,608) and 2026-07 = 76% (n=832). By year: 2012 56% -> 2025 14%, then 2026 68%. The ramp is abrupt: 2026-06-01/02 have ~10 papers/day, from 2026-06-03 ~130/day. Title+abstract contains one of the 33 focus phrases: 82% for 2026-01..05 (n=826), 72% for 2012-2025, **8% for >=2026-06 (n=3,440)**. Joined to `ingest_state.updated_at`: 2026-07-14 ingest day = 655 papers, all published 2026-07, 86% off; 2026-07-18 = 3,644 papers (2,256 from 2026-06), 56% off; later days (07-19..07-26) 17-20% off. So the first two seed batches (4,299 papers, 35% of the corpus) carry 2,400+ of the 4,630 off papers.
- Mechanism [VERIFIED code, INFERRED cause]: `rag/harvester.py:280` builds `all:"<term>"` (phrase-quoted, field-scoped to `all:`), `:288` appends `AND (cat:a OR cat:b)` only if `arxiv_categories` set, `:291-293` appends `submittedDate:[..]` only if dates set. `fetch()` (`:304-355`) issues one request per term, `sortBy=submittedDate&sortOrder=descending` for `freshest_first`. Real request from `prefetch.log`: `search_query=all%3A%22causal+inference%22&start=0&max_results=100&sortBy=submittedDate&sortOrder=descending`. The query is not loose in code (T-DOC11 quoting, commits `29fbddd`/`942bdc2`, 2026-07-14), and `_build_query` is date-independent, so a code bug cannot explain a step at 2026-06-03. What the data shows is that the newest ~8 weeks returned by the API for these quoted queries are mostly papers with no phrase in title or abstract (examples ingested: "On Thread Convergence" cs.PL, "UMoE: Unlocking Every Expert in Domain-Specific Training" cs.CL, "MET: ... Multilingual Moral Reasoning" cs.CL, 2607.11xxx). Candidate causes, none testable offline: (a) arXiv matches `all:` against a fresh-document field set (comments/full metadata/unindexed text) or falls back to token-OR for not-yet-fully-indexed papers; (b) a search-backend change around 2026-06-03. For the pre-2012 tail (197 papers, 83% off, e.g. `0705.1476` nucleon form factors, `0705.2064` "EMC effect ...") no phrase/abstract match either, consistent with tokens like "effect"/"model"/"in" (91% of off papers contain "in", 49% "inference", 47% "model", 14% "causal" - 99.9% of off papers share at least one query token with the config).
- Per-query supply [VERIFIED from `prefetch_seed30k.log`/`prefetch.log`, last `start` offset reached per query]: `causal inference` ~3,700 hits, `difference-in-differences` ~2,240, `causal discovery` ~1,230, `treatment effect estimation` ~680, `structural causal model` ~600; 9 queries (`econometric causal inference`, `panel data causal effect`, `large language model causal reasoning`, `causal reasoning language model`, `causal agent reinforcement learning`, `CausalML uplift modeling`, `EconML heterogeneous treatment`, `LLM causal inference`, `DoWhy causal inference`) return 0-1 hits - they are dead queries (n=0 papers with the phrase in the corpus). Sum of "candidate papers found" across logs = 9,326-9,433, yet the DB holds 12,385: ~3,000 papers came from earlier runs (07-14, 07-18; seed on `freshest_first`, then `ordering: relevance` + `arxiv_date_from 2024-01-01` runs on 07-19/07-24 visible in `ingest_run-3995-20260719*.log`, `ingest_run-7500-20260719*.log`), whose harvest logs were not retained (only MinerU/TEI output survives in `ingest_2000_*.log`, `ingest_run-3995-20260718*.log`). This is the main reason attribution is unrecoverable (F-5.2).
- Impact: 2,798 papers (22.6% of the corpus) are noise from one effect; ~2,800 MinerU parses + summaries + embeddings were spent on them; any future one-shot top-up with `freshest_first` will re-ingest the newest 6-8 weeks, i.e. the same contamination. Affects every consumer of the main corpus and any retrieval eval that does not stratify by label.
- Checklist dimension: 6 (changeability/reversibility) and 7 (evidence/measurement) - an unobserved external dependency drives corpus quality.
- Proposed change: no reharvest. (1) Ask the operator to run ONE manual `curl` of `all:"causal inference"` sorted by date and eyeball the first 100 titles to confirm the cause (I did not call the API). (2) Treat `submittedDate` within ~8 weeks of the harvest date as "unsettled": either gate them with F-5.3 or re-query them later.
- Needs: GPU no; foundation-protected path no; operator sign-off for the manual API check yes; re-embed no.
- How to verify: re-run `a3.py`-style phrase-in-text rate on the next batch of the newest 8 weeks: pass = >=70% of the batch contains a focus phrase (as for 2026-01..05), fail = ~8%.

### F-5.2 No query attribution, no topic label, no harvest provenance is stored anywhere  (severity: high)
- Evidence [VERIFIED]: `papers` columns are `paper_id, version, title, abstract, authors_json, categories_json, published, updated, pdf_path, markdown_path, relevance_score, doc_type, raw_affiliations, author_orgs` (no query/run/harvest-time column). `PaperRef` (`contracts/harvester.py:12-31`) has no `matched_query`. `Harvester.harvest` merges all terms into `latest: dict[paper_id, ref]` (`rag/harvester.py:~99-103`), discarding which term yielded the ref. `ingest_events_*.jsonl` carry only `RUN_START/STAGE_*/RUN_END` with counts - no paper ids (13 files grepped: zero per-paper events). Ingest time is recoverable only as `ingest_state.updated_at` day (last-stage time, not harvest time). PRD §8 (lines 528-536) specified "(2) harvest-precision spot-check ~50 causal/not" and "(3) query attribution - log which query term pulled each paper (prune noisy queries before adding a filter)"; neither was built (the first labelling of any kind is today's census). Archived configs: the 4 `config_run-*.yaml` files are byte-identical (md5 `7c0a198b...`; 34 queries ordered differently from live config, `relevance_filter: off`, `arxiv_categories: null`, dates null). Earlier runs (07-14/07-18/07-19/07-24) have no archived config at all, and `.run_overrides/run-*` directories were not preserved. So "did queries/categories/filter change between runs" can be answered only for the last 4 runs (no) and not for the runs that harvested 60%+ of the corpus (unknown).
- Impact: the PRD's own "prune noisy queries" step is impossible; every contamination question has to be reverse-engineered from titles. Cost to the operator today: this review.
- Checklist dimension: 7 (evidence/rationale), 3 (information hiding turned into information loss).
- Proposed change: add `matched_queries: list[str]` to `PaperRef`, accumulate in the `latest` merge (`rag/harvester.py` ~line 100), persist as a side table `paper_harvest(paper_id, query, run_id, harvested_at)` created by a numbered migration (new table, not an ALTER on `papers`, so the migration is additive and no existing-row backfill is needed). Backfill for the existing corpus is unknowable except by phrase match against title+abstract (which F-5.1 shows is ~85% for on-topic): store that as `query_guess` flagged `inferred=1`.
- Needs: GPU no; foundation-protected path YES (DB schema/migrations are protected per the programme brief; needs operator sign-off); re-embed no.
- How to verify: after the next harvest, `select count(*) from papers p left join paper_harvest h using(paper_id) where h.paper_id is null` over the new batch = 0.

### F-5.3 A lexical, GPU-free harvest-side gate would have removed most of the noise and is the cheapest fix  (severity: high)
- Evidence [VERIFIED by running the rules on all 12,385 labelled papers; rule applies to `PaperRef.title`+`abstract`, available at harvest]: 

| rule | kept | precision(on) | recall(on) | off share of kept |
|---|---|---|---|---|
| none | 12,385 | 0.542 | 1.000 | 37.4% |
| title+abstract contains a focus PHRASE | 6,691 | 0.851 | 0.849 | 5.3% |
| contains causal*/counterfactual/treatment/instrumental/confound/propensity/uplift | 8,093 | 0.796 | 0.960 | 10.5% |
| the above, and primary category not in physics set | 7,928 | 0.807 | 0.954 | 9.4% |
| ANY category in {stat.*, econ.*, cs.LG, cs.AI, math.ST} AND (phrase OR causal word) | 7,309 | 0.846 | 0.921 | 6.1% |
| `relevance_score` >= 0.35 | 6,312 | 0.851 | 0.800 | 8.2% |
| `relevance_score` >= 0.40 | 4,260 | 0.930 | 0.590 | 2.7% |

  ("on" recall counts only `on`; `borderline` is in the denominators of "off share kept" as non-on-non-off, i.e. off share is off/kept.) The word-level gate costs nothing at harvest time and applies before MinerU. It is exactly the gate `relevance_filter` was meant to be but evaluates the abstract the harvester already holds, so it needs no embedding and no GPU, unlike the `"embedding"` value (never implemented: only `contracts/config.py:37` mentions it; `grep relevance_filter` over app/rag/scripts: zero consumers; OG-36 in `docs/CORPUS-EXPANSION-RESEARCH.md:64`).
- Impact: applied to a replay of the existing corpus it would have dropped ~4,700 papers, 90% of them off, and kept 92-96% of on-topic.
- Checklist dimension: 2 (depth - a config field that promises a filter and does nothing is an interface that lies), 6.
- Proposed change: implement `relevance_filter: "lexical"` as a pure predicate applied in `Harvester.harvest` just before the `yield` at `rag/harvester.py:148` (reuse the `norm`/phrase matcher; one function ~15 lines). Counts of dropped refs logged, and the drop list written (needed for F-5.5 audit). Keep `off` default so the operator's mixed-corpus decision is not overridden; make it a per-run setting. Do NOT apply a category allow-list as the sole gate: it fails on the 2026-06+ cohort (cs.LG+cs.AI+stat+econ keeps 1,866 of 3,440 papers with a 70.5% off share; stat/econ only keeps 474 with 30% off but loses 43% of the cohort's on-topic papers, and 28% of on-topic papers overall).
- Needs: GPU no; foundation-protected path no (`rag/harvester.py`, `contracts/config.py` are ordinary code; `Config` is a frozen contract so a new Literal value needs the usual contract test); operator sign-off on default; re-embed no.
- How to verify: unit test with fixtures from `topic_labels.tsv` (e.g. 200 sampled rows): pass = on-recall >= 0.9 and off-share-kept <= 0.10; and a dry run against a recent arXiv batch recorded in the stop-loss (F-5.5).

### F-5.4 `relevance_score` is informative but is a poor design for gating, and its threshold was never set  (severity: medium)
- Evidence [VERIFIED code + computed]: `rag/orchestrator.py:487` `text = " ".join(self._config.focus_area_queries)` - one embedding of all 33 queries concatenated; `:684` `relevance_score = _cosine(summary_vec, topic_query_vec)`. Distribution by label (n, all non-null): on 6,711 median 0.417 [p5 0.276, p95 0.521]; borderline 1,044 median 0.328; off 4,630 median 0.256 [p5 0.109, p95 0.378]. AUC(on vs off) = 0.923. Best simple threshold reproduces the phrase rule (>=0.35: P 0.851 / R 0.800) and is dominated by the lexical gate (F-5.3) in recall at the same precision. A joined 33-term vector is a centroid of heterogeneous sub-topics (DiD, LLM reasoning, discovery); a paper strongly on one sub-topic is pulled toward the mean of the others, so it dilutes. 9 of the 33 queries are dead (F-5.1) yet still in the joined text. It is computed after parse+summarize+embed (`_finish`), so it can never save the MinerU cost, which is >80% of the spend. PRD §8 said "set the bar after smoke-test data"; no bar exists, and `ingest_local.py:436-438` explicitly declines to score drop-ins.
- Impact: low today (nothing reads it) but any future `embedding` filter would be tuned on an uncalibrated, lossy score. The off-share of kept papers at its operating points is 8%/17% (0.35/0.30), worse than the lexical gate.
- Checklist dimension: 2, 7.
- Proposed change: keep the stored score as-is (do not recompute; it is a clean historical signal). If an embedding signal is wanted later, compute per-query MAX similarity (`max_q cos(summary_vec, query_vec_q)`) plus the existing score, stored as a second column. CPU-only test today is not possible for the embedding variant (summary vectors live in Qdrant, down; query vectors need TEI, also down). What CAN be tested from SQLite alone is already done above (category and lexical rules). When Qdrant is back: scroll the `summaries` payload vectors (read-only) for the 12,385 papers, embed the 33 query strings once, compute max-cos, and report AUC vs labels next to 0.923.
- Needs: GPU/TEI yes for the embedding test (a one-time 33-string embed; could be done on CPU with the same model if TEI isn't available, but not the same model); foundation-protected no; re-embed no.
- How to verify: AUC(max-cos vs labels) - pass: >= 0.95 and > the 0.923 baseline; otherwise stay lexical.

### F-5.5 A deliberately mixed corpus needs stored labels, a batch monitor and a stop-loss; none exists  (severity: high)
- Evidence [VERIFIED]: the repo has no per-paper topic field and no contamination metric in `app/corpus_integrity.py` (88 lines; checks only that a `done` paper has >=1 chunk and >=1 block). The only labels are a TSV in an eval-data directory, outside the DB and outside backups. `build_corpus` finishes `completed` when supply is exhausted (BACKLOG O-1) and has no quality signal.
- Impact: the operator has chosen to keep the off-topic papers and to measure whether retrieval stays focused. That is a controlled-variable design; with no stored label, a future ingest that raises the off share from 37% to 50% is invisible, and any retrieval-focus measurement silently changes denominator.
- Checklist dimension: 7 (evidence), 6.
- Proposed change (smallest set that makes the mix a controlled variable):
  1. **Label storage: a sidecar table, not a `papers` column and not category tags.** `paper_topic(paper_id PRIMARY KEY, label CHECK in ('on','borderline','off'), source TEXT, rubric_version TEXT, labelled_at TEXT)` created by an additive protected migration (it is a new table, so no `papers` rewrite, and `papers` is the hot table retrieval joins). Load today's `topic_labels.tsv` with `source='llm-abstract-2026-11-10'`, `rubric_version='frozen-2026-11-10'`. Rejected: Qdrant payload tag (Qdrant is derived and rebuildable; the label must survive a reindex; and CQ-5 is already using category tags for standards metadata, a different axis); rejected: `papers.topic_label` column (ALTER on the foundation table; `put()` upsert at `rag/document_store.py:173-195` lists columns explicitly, so an extra column would be dropped on re-put unless edited).
  2. **Contamination monitor on every new ingest batch:** reuse `RUBRIC.md` and the same labelling prompt on each batch of new `PaperRef`s (title+categories+abstract excerpt, ~1 call per 50 papers; the labels come from LLM-in-the-loop work, so this should be a dispatched check, not an automatic API spend) - or use the F-5.3 lexical predicate as a free proxy (precision 0.85/recall 0.85) and sample 50 per batch for hand-labelling (the PRD's original spot-check).
  3. **Stop-loss:** `build_corpus` computes per-run off-share (lexical proxy, or labelled sample) and refuses to continue past the first 500 papers of a run if the share is > corpus off share + 10 points (today: >47%), using the existing `completed`/`failed` finish path; log the decision. Threshold is the operator's call (Q1).
  4. **Forward attribution:** F-5.2.
  5. **Stratify downstream:** every retrieval eval report must carry the label (EV-* strata report). Pin `rubric_version` so labels are comparable.
- Needs: GPU no; foundation-protected path YES for the migration (new table); operator sign-off yes (default threshold, spend on labelling calls); re-embed no.
- How to verify: `select label, count(*) from paper_topic group by 1` = 6,711 / 1,044 / 4,630 immediately after backfill; every new batch yields a recorded share; fault-inject a synthetic batch with 60% off papers and confirm the stop-loss halts.

### F-5.7 On-topic supply is understated by "exhausted"; the gap is phrase-recall, not volume  (severity: medium)
- Evidence [VERIFIED numbers, INFERRED conclusion]: BACKLOG O-1 (line 529) says arXiv is "near-exhausted for the current query filters" at 12,333 done (last prefetch: `11556/30000 cached, only 6 new available`). On-topic arrivals are flat: `on` per month 2025-02..2026-05 = 70-164 (median ~110), with 2026-06 = 245 (more candidates because 2026-06 was harvested in the first seed). 6,711 on + 1,044 borderline = 7,755 relevant papers, i.e. the "12,333 total" is 63% relevant, not 100%. Query design: 9 of 33 queries return 0-1 hits; 14 return <=200. Everything outside these phrases (e.g. causal-adjacent terms: "mediation analysis", "off-policy evaluation", "uplift", "interference", "A/B test", "counterfactual explanations", "Granger causality", "transfer entropy" - all named in `RUBRIC.md` as on-topic) has no query. The docs `ONBOARDING_AND_ARXIV_KEYWORDS.md` §2b.1-2b.4 (the Waymo strategy) shows the working pattern: `cat:<list> AND abs:"<phrase>"` AND-combined with a category priority list and explicit exclusions; the main corpus never used it (no `cat:`, `all:` instead of `abs:`).
- Impact: a true on-topic supply is larger than 7.7k; "exhausted" is a harvest-design limit. Not measurable offline; I did not call the API.
- Checklist dimension: 7; 4 (design process - the Waymo lesson was not carried back to the main corpus).
- Proposed change: a second harvest config (operator-gated, new `focus_area_queries` file) using `cat:stat.ME OR cat:econ.EM OR cat:stat.ML ... AND abs:"mediation" ...` per RUBRIC topics, dated `arxiv_date_to: 2026-05-31` to avoid the unsettled window of F-5.1, plus F-5.3 lexical gate and F-5.2 attribution so the yield per query is visible. Before any ingest: harvest-only dry run reporting new ids per query (the existing `prefetch_pdfs` "N candidate papers found" phase already does exactly this without downloading).
- Needs: GPU no for the dry run (network yes); operator sign-off yes; re-embed no.
- How to verify: dry-run yields N new ids/query; pass = >=50% of a 50-id hand-labelled sample is `on`.

### F-5.8 Stale versions are never refreshed; `version` is tracked but frozen at harvest time  (severity: medium)
- Evidence [VERIFIED]: `papers.version` distribution: v1 7,768 (62.7%), v2 2,690, v3 1,145, v4 442, v5+ 324. `Harvester.harvest` skips any `paper_id in self._seen_ids` (`rag/harvester.py:148`) - ids ingested once are never re-fetched, so a paper harvested as v1 never picks up its v2/v3 text. For papers harvested within weeks of submission (the 2026-06/07 cohort of 3,440), v1 is likely to be superseded; older ids may be v-latest only by luck. Also `_version_num` dedup compares only versions seen in one harvest. Quarantined papers get re-tried, and the evidence of staleness is real: 53 of 80 quarantine rows are `HTTP 404` on `arxiv.org/pdf/<id>v2` etc. (43 of them have since recovered; they sit in both `papers` and `quarantine`).
- Impact: wrong-version citations for the minority of papers revised after ingestion; for a research corpus used for citation this is a small but silent grounding error. Frequency: unknown without the API (INFERRED).
- Checklist dimension: 6.
- Proposed change: not a refresh pipeline (YAGNI). One query-by-id check (`ArxivSource.fetch_by_ids`, `rag/harvester.py:357`, already exists) reporting how many ingested ids have a newer `version`/`updated` than stored - read-only report first; refresh only if the rate is material. Reuse `fetch_by_ids`; none other exists.
- Needs: GPU no; foundation-protected no; sign-off no for the report; re-embed only if refresh later chosen.
- How to verify: a sample of 300 ids: pass = <5% newer; otherwise propose a re-ingest of changed ids.

### F-5.9 Quarantine table holds stale rows and mixes causes; harmless but not self-cleaning  (severity: low)
- Evidence [VERIFIED]: 80 rows: 53 PDF 404 (arXiv indexes metadata before PDF; 54 rows dated 2026-07-14, i.e. the first seed hitting 2607.x papers), 16 GROBID reference-extraction 500, 9 MinerU CUDA out-of-memory, 1 arXiv API 500, 1 other. 60 of 80 quarantined ids exist in `papers` today (recovered on a later run; `quarantine` row not removed), only 20 are truly absent. The orchestrator intentionally re-tries (`rag/orchestrator.py` `harvest` docstring); `_state.quarantine` is first-reason-wins.
- Impact: a count of "80 quarantined" overstates loss by 3x; anyone using `quarantine` as the failure metric is misled.
- Checklist dimension: 3.
- Proposed change: a read-only report `quarantine rows whose paper_id is in papers and ingest_state=done` (60) and delete those rows in a maintenance script on operator sign-off; do not change the retry semantics.
- Needs: GPU no; foundation-protected path yes (DB write); sign-off yes; re-embed no.
- How to verify: `select count(*) from quarantine q join papers using(paper_id)` = 0 afterwards; 20 rows remain.

### F-5.11 The four other corpora cannot be rebuilt from tracked files  (severity: medium)
- Evidence [VERIFIED]: `git ls-files | grep -i "_tools|corpora|config.*(waymo|standards|motional|waabi)"` returns nothing. The `config.yaml` of each lives only in its data directory (e.g. `research-system-rag-standards/data/config.yaml`: `focus_area_queries: [autonomous vehicle safety standards and regulation]`, `corpus_cap: 33`, `collection: av_standards`, `ingest_paper_ids: [1708.06374, local:0147e45dfd6e, ...]`). Build scripts `_tools/build_standards.sh`, `ingest_completion_*.sh`, `build_motional.sh`, `build_waabi.sh`, `fetch_motional.py`, and `catalog.json`/`questions.json`/`q*.json` all live in untracked data directories.
